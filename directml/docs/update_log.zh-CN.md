# MiniMind --- 更新日志

> **历史 DirectML 归档 — 更新日期：2026-09-24**
>
> DirectML 已不再作为 MiniMind 的训练后端。M5 最终验证发现了一个特定于测试的 DirectML FP16 路径的数值偏差问题。以下历史结果仍被保留，用于可复现性和工程参考；ROCm 开发情况另作记录。

本文件提供了对 MiniMind DirectML 分支主要变更的按时间顺序记录。

有关技术问题、原因及解决方案，请参见 [`directml_issues.md`](directml_issues.zh-CN.md)。

有关持久性的架构决策和技术经验，请参见 [`project_memory.md`](project_memory.zh-CN.md)。

<a id="m4-----performance--stability"></a>
# M4 --- 性能与稳定性

-   开始在DirectML上进行真实数据预训练的性能和稳定性验证。
-   增加了使用`--max_steps`的有界真实数据训练运行，以使DirectML基准测试变得可行。
-   确认使用真实MiniMind预训练数据集实现了持续的预训练执行。
-   对明确选择的`directml:1`适配器上的训练进行了基准测试。
-   测试了使用完整`max_seq_len = 340`配置的真实训练。
-   验证了使用`batch_size = 8`和`max_seq_len = 340`的真实数据执行。
-   验证了使用`batch_size = 8`和`max_seq_len = 340`的100步有界真实训练运行。
-   确认`32 × 340`在真实训练中因GPU内存不足而失败。
-   确认`16 × 340`可以完成累积周期，但之后因GPU内存不足而失败。
-   建立了`8 × 340`与梯度累积`8`作为当前真实训练的参考配置。
-   在参考基准测试中测得约`11.62 GB`的专用GPU峰值内存。
-   通过梯度累积在保持物理批次大小与DirectML内存约束兼容的同时，实现了更大的有效批次大小。
-   在性能测量前增加了预热步骤，以避免将初始化开销包含在稳态时间中。
-   初始真实训练测量值约为 `5.280 s/iteration`、`1.52 samples/s` 和 `304.81 effective tokens/s`。
-   调查了训练测量值异常缓慢的问题。
-   识别出训练测量路径中存在不必要的 DirectML 到 CPU 的同步操作。
-   从关键训练和测量路径中移除了不必要的同步操作。
-   在修正后，重新运行了相同的 `8 × 340` 参考工作负载，共执行 100 步。
-   测量值约为 `0.482 s/iteration`、`16.61 samples/s` 和 `3341.37 effective tokens/s`。
-   测量值约为 `5647.46 padded tokens/s`。
-   与初始基准相比，测量的迭代时间减少了约 `10.95×`。
-   将估计的每个周期持续时间从约 `9.70 days` 减少至 `21.24 hours`（`0.89 days`）。
-   确认性能提升是在不减少模型架构、批处理大小、序列长度或梯度累积配置的情况下实现的。
-   确认 AdamW `aten::lerp.Scalar_out` 的 CPU 降级仍然存在，但无法解释初始的全部性能下降。
-   确立了基于步数的运行作为 DirectML 性能和稳定性的首选验证方法。
-   将合成的 DirectML 兼容性基准与真实 MiniMind 训练行为进行了对比。
-   确认通过合成兼容性基准的配置并不能保证在真实训练数据下仍保持实用或稳定。
-   识别出 `batch_size` 和 `max_seq_len` 是相互作用的内存约束，而非独立的兼容性限制。
-   确认较小的物理批处理大小为完整序列长度提供了显著更大的余量。
-   识别出在 AdamW 执行过程中，对于不支持的操作（如 `aten::lerp.Scalar_out`）会触发 DirectML CPU 降级。
-   确认该降级不会阻止训练，但会引入一个潜在的性能瓶颈。
-   区分了 DirectML 设备兼容性与实际端到端训练性能。
-   确认在多 GPU 系统上获得可重复基准结果仍需显式选择物理适配器。
-   记录了合成兼容性结果与真实数据训练观察之间的差异。
-   整合了 DirectML 基准方法和结果，用于未来的回归测试。

当前结论：

``` text
DirectML compatibility
        ↓
Synthetic benchmark
        ↓
Real-data bounded training
        ↓
Performance / fallback analysis
        ↓
Practical configuration
```

当前真实数据 DirectML 验证的实际参考配置为：

``` text
Device:              directml:1
Batch size:          8
Max sequence length: 340
Gradient accumulation: 8
```

该配置是当前的 **验证和基准测试基线**。

最终 M4 验证还：

-   确认在测试的纯 FP16 路径中，默认的 AdamW ε `1e-8` 在第一次优化器更新后变为非有限值；
-   通过首次优化器更新边界验证了完整的有界 FP16 兼容性矩阵；

-   将 DirectML 的 FP16 处理和全局 `--max_steps` 支持传播至预训练、完整 SFT、LoRA、蒸馏、GRPO、Agent RL 和 PPO；
-   新增了 `tests/test_all_trainers.py`，用于显式验证 DirectML 训练器的烟雾测试；
-   成功验证了烟雾测试套件中包含的所有训练器；

-   避免了验证过的右填充 Agent 重新计算中存在问题的注意力掩码路径，并保留了对数值敏感的 RL 计算使用 FP32；

<a id="m5-----project-finalization"></a>
# M5 --- 项目最终化

-   诊断出一个长期运行的密集层预训练崩溃问题，其中先前的纯FP16优化器路径虽保持有限但收敛于token自我复制。
-   为密集层DirectML FP16预训练增加了FP32主权重，并通过全局步长`1100`验证了修正路径，诊断损失为`6.7506`，Top-1准确率为`6.30%`，重复率为`0.89%`。

-   在顺序训练流程中增加了训练器特定的批大小、序列长度和累积设置，同时将M4的`8 × 340`配置记录为持续DirectML预训练的基准配置。
-   增加了训练器特定的周期性恢复检查点，并记录了中断训练的恢复流程，使用`--from_resume 1`。
-   发现DirectML在填充的因果语言模型批次上存在错误的平均值计算，标识为`cross_entropy(..., ignore_index=-100)`。
-   将隐式平均值计算替换为显式的有效token损失归一化。
-   将目标DirectML损失验证工具从`scripts/`移动至`tests/`。
-   在步长`100`处验证了一次全新的修正FP16 + FP32主权重预训练运行，损失为`7.3925`，Top-1准确率为`3.26%`，重复率为`3.26%`。
-   在步长`1000`处对同一运行进行了验证，损失为`6.7785`，Top-1准确率为`6.76%`，重复率为`0.76%`。

-   从零开始重新启动密集层预训练，采用修正后的FP16计算 + FP32主权重 + 有效token损失路径以及上游预训练参数。
-   成功完成了首次完整的密集层预训练周期，物理步长为`batch_size = 32`。
-   在样本`0–255`上验证了第1个周期的检查点，使用带令牌加权的全局损失`6.1017`，Top-1准确率`15.07%`，Top-1重复率`0.83%`，以及平均熵`5.3160`。
-   确认了模型损失与独立手动进行的令牌归一化交叉熵（`6.48799419`）之间完全一致，参考批次的差异为`0`。
-   将之前报告的约在`12–13`处的聚合诊断损失识别为`diagnose_pretrain.py`聚合问题，而非训练发散。
-   开始修正`diagnose_pretrain.py`，使其使用实际的批量训练损失路径和带令牌加权的聚合。

-   使用`sum / valid`的相同logits，按令牌`none → FP32 mean`，以及CPU FP32参考归约，重新测试了DirectML因果语言模型损失。
-   确认最初在测试DirectML FP16路径上使用的`reduction="sum" / valid_tokens`补救措施也是错误的。
-   替换为`reduction="none"`，随后对有效非填充令牌进行FP32平均。
-   验证了最终批量大小为32的损失路径，模型损失为`6.30274916`，与CPU FP32参考值`6.30530691`对比（差异约为`0.00256`）。
-   将已完成的两个周期/早期完整周期预训练检查点重新分类为中间调查的产物，因为其反向传播使用了已被取代的`sum / valid`归约。
-   最终的Dense预训练必须从头开始，使用FP32主权重和最终按令牌FP32有效均值交叉熵路径。
-   通过步骤 `1200` 验证了最终的 DirectML FP16 + FP32-master + 每个标记交叉熵路径。
-   训练路径和手动标记损失在两个独立的 256 样本评估区域中均保持在大约 `0.003` 的范围内。
-   在步骤 `1200`，训练路径损失达到 `6.3752` 和 `6.3568`，Top-1 准确率达到 `8.66%` 和 `8.91%`，Top-1 重复率限制在 `1.96%` 和 `2.08%` 以内。
-   确认未出现历史自复制崩溃的复发；在整个后续完整周期中均未观察到复发现象。
-   完成了使用 FP16 计算、FP32 主权重和每个标记 FP32-有效均值交叉熵的最终 Dense DirectML 预训练运行的第一个周期。
-   在样本 `0–255` 上，验证训练损失 `6.0612`，手动损失 `6.0637`，Top-1 准确率 `13.71%`，重复率 `0.81%`，以及平均熵值 `5.3487`。
-   在样本 `100000–100255` 上，验证训练损失 `6.0177`，手动损失 `6.0201`，Top-1 准确率 `13.80%`，重复率 `0.71%`，以及平均熵值 `5.3436`。
-   在完成一个完整周期后，确认训练损失与手动损失的差异约为 `0.0025`，且未出现历史自复制崩溃的复发。
-   完成了最终修正的 Dense DirectML 预训练运行的第 2 个周期。
-   在来自四个数据集区域的 `4,096` 个样本上评估了最终检查点；训练损失与手动损失保持高度一致，Top-1 重复率仍低于 `1%`。
-   通过定性生成确认，历史重复标记崩溃未再次发生。
-   最初保留了第2个周期的检查点作为密集预训练的基础模型，但在最终的定性分析和跨后端模型质量验证后将其排除。
-   将上游CUDA混合精度与DirectML路径进行了对比，确认上游在保持FP32模型参数的同时，使用BF16自动转换来支持计算操作。
-   测试了类似上游的DirectML BF16张量路径；当前DirectML后端在首次训练步骤之前就拒绝了`BFloat16`。
-   重新测试了不使用FP32主权重的密集预训练，采用直接在FP16模型参数上进行AdamW更新的方式。
-   在步骤`1000`，快速的直接FP16检查点产生了诊断损失`9.2573`，Top-1准确率`0.31%`，以及重复率`0.29%`。
-   在步骤`2000`，诊断损失降至`8.3102`，Top-1准确率提升至`0.92%`，而重复率上升至`1.20%`。
-   在步骤`5000`，诊断损失进一步改善至`7.3196`，但Top-1重复率急剧上升至`39.24%`，而真实数据的重复率仍保持在大约`0.29%`。
-   将直接FP16优化器路径作为持续训练策略予以拒绝，并保留FP16计算、FP32主权重以及FP32 AdamW更新。
-   开始通过将诊断的DirectML到CPU标量同步限制在`log_interval`边界，而不是每个批次或优化器更新，来优化所保留的稳定路径。
-   在每次优化器步骤中，保持梯度裁剪、FP32主权重更新以及主权重到模型的同步不变。
-   在相同的DirectML预训练配置下，对稳定训练器和日志同步训练器进行了`1000`步的基准测试。
-   测量了稳定训练器的`2003.79 s`和日志同步训练器的`1930.75 s`。
-   每步平均耗时从`2.0038 s`减少到`1.9307 s`，对应了`1.038×`倍的速度提升和`3.65%`时间减少。
-   日志同步训练器的吞吐量验证已完成；检查点质量验证仍待完成，因此尚未成为最终参考训练器。

<a id="m5-----final-directml-quality-assessment"></a>
# M5 --- 最终DirectML质量评估

-   在执行、损失和优化器修复后，重新评估了最终本地训练的密集预训练检查点。
-   确认了分词器的编码/解码功能正确，且`pretrain_t2t_mini.jsonl`数据集可读且连贯。
-   使用相同的`eval_llm.py`路径评估了官方上游的`pretrain_768.pth`检查点。
-   确认了在CPU和`directml:1`上，官方检查点的生成结果是连贯的。
-   确认本地训练的DirectML第1周期检查点是不连贯的。
-   确认本地训练的DirectML第2周期检查点也是不连贯的。
-   排除了分词器、数据集、检查点加载器和DirectML推理路径作为质量差距主要原因的可能性。
